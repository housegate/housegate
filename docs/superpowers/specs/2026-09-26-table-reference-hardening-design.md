# Table-reference hardening — Design

**Status:** design. The policy was approved on 2026-09-25 ("同意，SI 开关都生效，按提案写 spec"); this document is the written form of that policy, grounded in the 2026-09-26 re-measurement.

**Repositories:** rewriter-proto, rewriter-go, rewriter-grpc (GitHub `housegate/rewriter`), housegate. sentio-node is not changed.

**Related:** [2026-08-25-storage-integrity-lexical-namespace-closure-design.md](2026-08-25-storage-integrity-lexical-namespace-closure-design.md) (Spec N: the `sireserved` lexical model this design generalises), [2026-09-24-dynamic-si-table-set-housegate-design.md](2026-09-24-dynamic-si-table-set-housegate-design.md) (the `sitablestate` gate and contract V2 this design hardens).

## 1. Goal

An ordinary session can only ever read or write a table that the rewriter resolved through the caller's `database_map` and reported in `AccessedTables`. Today that invariant holds for the FROM clause and for write targets, and nowhere else. Four families of statement escape it:

- **Identifier parameters.** `{p:Identifier}` in a table position is bound by ClickHouse at execution time. Both engines forward it in read positions without reporting it; the native engine also emits `phys.""` for write targets and the C++ engine crashes on `SHOW CREATE TABLE {p:Identifier}`.
- **Physical and protocol-owned names.** The shared physical database (`phys` below) and `hg_safe` / `hg_unsafe` / `hg_promote` can be named directly in every position the rewriter does not rewrite: IN operands, `INSERT … SELECT` and `CREATE TABLE … AS SELECT` sources, table-function and table-engine arguments, and string-form lookups. Under storage integrity the `hg_*` names are refused in those positions but the ordinary physical table behind an Active table is not.
- **Unreported sources.** The positions above are never rewritten and never reported, so the permission observer cannot see them, and the `sitablestate` gate and the ingress cannot govern them. The same gap breaks legitimate SQL: a tenant's own `INSERT INTO db1.o SELECT * FROM db1.o` is forwarded with the logical source name, which ClickHouse cannot resolve.
- **Housegate's own fail-open paths.** With storage integrity disabled every non-`Success` rewriter answer forwards the original SQL; `sitablestate` decodes backslash escapes differently from ClickHouse; the exception scrubber and `sireserved` do not know `hg_promote`.

After this design both engines implement one table-reference policy (§5) that is identical with storage integrity enabled or disabled, every finding is pinned in the shared corpus, and housegate fails closed on every engine rejection, adds a lexical guard for ordinary sessions as defence in depth, and refuses to start against an engine that does not prove the policy.

## 2. Measured facts this design rests on

Measured on 2026-09-26 against the released native engine (rewriter-go v0.13.0 = `origin/main` ac49dee, FFI asset built from Polyglot v0.12.1) with the request housegate sends: `database_map {db1: phys}`, `known_physical_databases [phys]`, logical context `db1`, delimiter `_`; with storage integrity v2 marking `db1.t` Active and `reserved_databases [hg_safe, hg_unsafe, hg_promote]`. 17 payloads (own, Active, a second mapped logical database `db2`, `phys` in backtick and double-quote form, the three `hg_*` databases, four parameter forms, three escaped forms, `system`) × 51 statement shapes × both SI states, plus class-only statements, follow-up probes and a run with `db2` left out of `database_map`: 1,750 cases, no transport errors. With `db2` unmapped, `SELECT * FROM db2.x` is forwarded verbatim and reported with logical database `db2` and no physical database, which the permission observer refuses; `… IN db2.x`, `INSERT INTO db1.o SELECT * FROM db2.x` and the CTAS source are forwarded verbatim and not reported; write and DDL targets, `USE db2` and `MV … TO db2.x` are `InvalidRewriteRequest`; `merge('db2', 'x')` passes unreported. The probe, generator, raw results and triage matrix are in `.superpowers/sdd/2026-09-26-table-reference-hardening/measurements/` (git-ignored, re-runnable; see its README). The C++ engine (rewriter-grpc v0.15.0 = `origin/main` 56a17b7) was measured on 2026-09-25 through the build-box probe container; that raw file was lost with the previous session's scratchpad, and its conclusions below come from the session record and from reading the v0.15.0 source. housegate is `origin/main` 04fb8c0; rewriter-proto is 192e43a.

**Defence layers, and which gaps are reachable.**
- The rewrite plugin runs on every session that is neither maintenance, platform-operator nor peer-trusted; driver sessions are ordinary for it ([pkg/plugins/rewrite/rewriter.go](../../../pkg/plugins/rewrite/rewriter.go)). With storage integrity disabled, `UnsupportedStatement` is an explicit pass-through of the original SQL ([pkg/rewriter/sentio.go](../../../pkg/rewriter/sentio.go) `Rewrite`, the `RewriteCode_UnsupportedStatement` arm) and every other non-`Success` code becomes a Go error that the plugin logs and forwards (`FailClosedOnError` is `siOptions.Enabled`, [build.go](../../../build.go)). Transport failures take the same path.
- With auth enabled, commitgate dispatches every classified statement type plus `Unspecified` to `PermissionCommitGateObserver` ([pkg/network/permission_commitgate_observer.go](../../../pkg/network/permission_commitgate_observer.go)): `Unspecified` is always refused; a type in `permissionPolicy` is checked per reported logical database; an empty `AccessedTables` passes only for `SELECT` and `SHOW DATABASES`; `system` is exempt for reads. Commitgate is skipped on maintenance, platform-operator and driver sessions, and is absent when auth is disabled.
- Therefore the reachable class on a production deployment is **`Success` with a table the engine did not report**, whatever the statement type. The `Unsupported → forward` path is reachable on driver sessions and auth-disabled deployments. The C++ engine's `Success + SELECT` classification of unmodelled classes passes the observer as a FROM-less SELECT even with auth on.

**Identifier parameters.**
- Native, both SI states: `{p:Identifier}`, `db1.{p:Identifier}`, `{d:Identifier}.t` in FROM, JOIN, subquery, CTE, UNION, IN and both source positions are forwarded verbatim with `AccessedTables` empty. A bare `{p:Identifier}` binds in the session's current database, which housegate set to the physical database, so it reads any table of any tenant and passes the permission observer as a FROM-less SELECT. `{p}` in write and DDL targets emits `phys.""`; `EXISTS TABLE db1.{p}` and `SHOW CREATE TABLE db1.{p}` emit ``phys.`db1.db1` `` and report `.db1`; `CREATE MATERIALIZED VIEW … TO db1.{p}` emits `TO phys.""`; `DESCRIBE db1.{p}` is forwarded verbatim; `RENAME TABLE {d:Identifier}.t …` emits unparseable text. The write-side outputs are refused by ClickHouse's parser by accident, not by policy. Anchors: `internal/engine/nodes.go:1324-1332` drops a target whose name is a parameter (`decodeTableTarget`, `nodes.go:2507-2511`); `nodes.go:386-388` and `421-423` drop a parameter-only IN operand; `nodes_test.go:1154-1169` and `1297-1307` pin the drop.
- C++ v0.15.0: parameters in every write and DDL target are refused with `query parameters are not supported as write targets` (`src/handlers/writes.cc:227-272`, `728-731`); `SELECT … FROM db1.{p:Identifier}` is rewritten to `phys.{p:Identifier}` (`select.cc:285-380`, `writes.cc:885-888` documents the mechanism); `CREATE MATERIALIZED VIEW … TO {p:Identifier}` keeps the execution-time target and reports only the view and the source (`writes.cc:591-605`); IN operands and both source positions are not reported; `SHOW CREATE TABLE` / `EXISTS TABLE` of a parameter reach `setTable("")` and then the formatter's unconditional dereference (`show_create.cc:75-76, 121-122, 152`, `exists.cc:76-77, 127-128, 159`): the service died on that request in the first 2026-09-25 run and survived it in the rerun, so the crash is treated as a real null dereference that the release build does not always hit, not as a flake; `DESCRIBE {p}` misses the target regex and, by source reading, falls through to the SELECT fallback as `Success`.

**Physical and protocol-owned names.**
- housegate always sends `known_physical_databases = [<physical_database>]` ([pkg/rewriter/sentio.go](../../../pkg/rewriter/sentio.go) `buildDatabaseMap`). Both engines then treat `phys` as a pass-through logical name: a direct `phys.x` in FROM, DML or DDL target becomes ``phys.`phys.x` `` (nonsense but harmless), and `USE phys` succeeds with `database_rewrites` empty. With `phys` absent from the list, `SELECT … FROM phys.x` is forwarded verbatim by the lenient SELECT walker (`select.go:284-285`; C++ `select.cc:378-379`).
- Positions that are never rewritten forward the name verbatim and never report it, in both engines and both SI states: the IN operand in every form (infix, parenthesised, tuple, `in()` call, `GLOBAL IN`), the `INSERT … SELECT` source, the `CREATE TABLE … AS SELECT` source, the arguments of `merge` / `remote` / `remoteSecure` / `cluster` / `dictionary` / `loop` / `mergeTreeIndex`, the arguments of `ENGINE = Merge / Buffer / Distributed`, and the first argument of `joinGet` / `dictGet*` / `hasColumnInTable`. Examples measured `Success`: `SELECT * FROM db1.o WHERE a IN phys.`db2.x``, `INSERT INTO db1.o SELECT * FROM phys.`db2.x``, `SELECT * FROM merge('phys', 'db2.x')`, `CREATE TABLE db1.n (a UInt64) ENGINE = Merge('phys', 'db2.x')`, `SELECT joinGet('phys.`db2.x`', 'v', 1)`.
- Under storage integrity v2 the `hg_*` databases and the caller's own SI-indexer logical databases are refused in those positions by the namespace policy (`internal/handlers/storage_integrity_policy.go`; C++ `storage_integrity.cc:1510-1597`), and `remote(…, phys.`x`)`, `Buffer(phys.`x`, …)` and `Distributed(default, phys.`x`)` in identifier form are refused as "not statically resolvable". But the string forms `merge('phys', …)` / `remote('h', 'phys', 'x')` / `Merge('phys', …)` pass, and the ordinary physical table behind an Active table is readable through every unreported position: `… WHERE a IN phys.`db1.t``, `INSERT INTO db1.o SELECT * FROM phys.`db1.t``, `CREATE TABLE db1.n ENGINE = Memory AS SELECT * FROM phys.`db1.t`` all return `Success` reporting only `db1.o` / `db1.n`. This bypasses the safe read surface.
- With storage integrity disabled the `hg_*` names are forwarded everywhere, including `SELECT * FROM merge('hg_safe', 'db1__t')` and `CREATE TABLE db1.n (a UInt64) ENGINE = Buffer(hg_safe.db1__t, …)` (a write path into `hg_safe`), and `SELECT * FROM hg_safe.db1__t` is forwarded verbatim and reported with logical database `hg_safe`, which only the permission observer refuses.
- Neither engine has a general notion of "the physical database" or of an `hg_` prefix: the only physical-name checks are the SI ones (native `nameresolve/resolve.go:301-399`, `contract.go:27-41`; C++ `storage_integrity.cc:901-946`).

**Sources of the caller's own tables.** `INSERT INTO db1.o SELECT * FROM db1.o` is emitted as `INSERT INTO phys."db1.o" SELECT * FROM db1.o`, and `CREATE TABLE db1.n ENGINE = Memory AS SELECT * FROM o` as `… AS (SELECT * FROM o)`: the source keeps its logical name and cannot resolve on ClickHouse. Under SI v2 `SELECT * FROM db1.o WHERE a IN db1.o` is refused with `storage-integrity logical database db1 is not directly addressable through IN table target`. Both engines (native `handlers/writes.go:507-515`, `engine/writes.go:126-140`; C++ `writes.cc:825-847`, `1009-1051`, tests `CreateTable_AsSelect_ReturnsTargetOnly` and `Insert_Select_ReturnsTargetOnly`). View and materialized-view bodies are the exception: both engines rewrite and report them (`writes.go:447-505`; C++ `writes.cc:607-621`).

**Unmodelled statement classes with storage integrity disabled.** Native returns `Success` with `STATEMENT_TYPE_UNSPECIFIED` and no tables for `SYSTEM`, `SET`, `EXPLAIN`, `CHECK TABLE`, `CREATE USER`, `CREATE FUNCTION` (`native.go:258-270`); C++ returns `Success` with `STATEMENT_TYPE_SELECT` (`select.cc:887-978`, pinned by `UnmodelledStatementPassesThroughWithoutStorageIntegrity`). `DETACH` / `ATTACH` / `UNDROP` / `OPTIMIZE` / `KILL` / `BACKUP` / `CREATE DICTIONARY` return `UnsupportedStatement`, which housegate forwards. Under V2 both engines refuse all of these (H6).

**Backslash escapes.** Both engines decode `\x74` inside a quoted identifier the way ClickHouse does: under SI v2 `SELECT * FROM db1.`\x74`` is rewritten to the `hg_safe` read, and `CREATE MATERIALIZED VIEW db1.mv TO db1.`\x74` …`, `CREATE MATERIALIZED VIEW db1.`\x74` …` and `CREATE TABLE db1.`\x74` … AS SELECT …` are refused as writes to the Active table. housegate's `sitablestate` tokenizer does not: `readQuoted` drops the backslash and keeps the next byte ([pkg/plugins/sitablestate/lexer.go](../../../pkg/plugins/sitablestate/lexer.go)), so it reads `x74` where ClickHouse reads `t`. The engine catches an Active target because it is in `StorageIntegrityArgs.tables`; a Pending, Refused or Gone table is known only to `sitablestate`, so its header decision is the only gate for those states, and it is wrong for an escaped name.

**Materialized view TO an Active table.** Native refuses it (`accepts writes only through the signed statement lane`, `handlers/writes.go:143-151` and `253-281`); C++ v0.15.0 accepts it, because `preflightStorageIntegrityWrite` never reads `create->targets` (`writes.cc:362-396`) and `applyDynamicRewrite` has no SI check (`name_rewrite.cc:159-222`). The only related corpus case, `si_create_materialized_view_body_rejected`, has the SI table as the source.

**Reserved-name lists in housegate.** `build.go` wires `sireserved` with `hg_safe` and `hg_unsafe` only, although `sitable.ReservedDatabases()` returns three names; `NewStorageIntegrityScrubber` redacts `hg_safe`, `hg_unsafe` and `_hg_row_id` only ([pkg/rewriter/storage_integrity.go](../../../pkg/rewriter/storage_integrity.go)).

**Data-only table functions.** `numbers`, `generateRandom`, `values`, `format`, `input` and `view(SELECT …)` pass with no reported table (the `view` body is walked); `url` and `s3` pass with no reported table.

**Existing pins that encode the current behaviour** and therefore flip under this design: rewriter-go `writes_cases.json` `insert_select_source_untouched`; `storage_integrity_cases.json` `si_ordinary_in_table_allowed`, `si_ordinary_local_catalog_function_allowed` (`mergeTreeIndex('other', 'u')` → no accessed table); `nodes_test.go:1154-1169`, `1297-1307`; `select_cases.json` `dynamic_unqualified_no_context_lenient`; rewriter-grpc `CreateTable_AsSelect_ReturnsTargetOnly`, `Insert_Select_ReturnsTargetOnly`, `UnmodelledStatementPassesThroughWithoutStorageIntegrity`, `RejectedBeforeRewriteInEveryMode` (message text). The shared corpus is 256 cases, 254,170 bytes, FNV-1a/64 `7051648083520101593`, byte-identical in both engine repositories.

## 3. Scope

**In scope:**
- the table-reference policy (§5) in both engines: identifier parameters, the protected namespace, source rewriting and reporting, the table-function and table-engine allowlists, string-form lookups, unmodelled classes;
- the `protected_databases` field in rewriter-proto;
- the C++ crash, the C++ classification of unmodelled classes, and the C++ `CREATE MATERIALIZED VIEW … TO <Active table>` refusal;
- housegate: fail-closed on every engine rejection with one explicit transport-failure switch, the ordinary-session lexical guard, the `sitablestate` escape refusal, `hg_promote` in the scrubber and `sireserved`, and a startup probe that proves the policy;
- shared corpus cases for every finding, and a recorded cross-engine differential run.

**Out of scope, deliberately (non-goals):**
- **`url`, `s3`, `file`, `hdfs`, `azureBlobStorage`, `gcs`, `iceberg`, `deltaLake`, `hudi` and their `*Cluster` table functions.** They read external data, not another tenant's table, so the table-reference invariant is not what they break; what they break is egress control (server-side request forgery, reading the server's filesystem), which belongs to ClickHouse's own user grants and `allowed_*` settings. They keep today's behaviour (forwarded, not reported) and are tracked as a separate follow-up that should start from the ClickHouse user configuration.
- **Filtered logical `system.*` reads (step 2).** Step 1 of the `system` database rule is in scope (§5, "The system database"): an allowlist refuses every `system` table that is not class (b), `clusters`, or a class (c) table the Sentio driver reads by physical name. Serving those class (c) tables as a filtered logical rewrite, and the sentio-core `chx` change that reads logical names in lockstep, is step 2, a follow-up issue; until it lands their passthrough is a known residual (§5). The earlier premise of this bullet, that ClickHouse enforces per-row visibility on `system.*`, is false for housegate: every tenant reaches ClickHouse as one shared user, so ClickHouse's per-user filters filter nothing between tenants (measured on 26.2 and 25.8, [system-tables-survey.md](system-tables-survey.md)).
- `GRANT` / `REVOKE` on databases outside the caller's map: they reach housegate as `privileges_deltas`, not as table accesses, and commitgate owns them.
- The `remote()` clauses that the rewriter itself emits for cross-indexer routing: they are engine output, not caller input, and the peer side runs them on a peer-trusted session.
- `sqlite` and `redis` table functions (Spec N D4 excluded them: their second argument is not a ClickHouse identifier).
- Any change to the storage-integrity read surface, the signed lane, or `sitablestate`'s decision matrix beyond the escape refusal.

## 4. Decisions

- **T1 — One policy, both SI states.** The policy applies to every rewriter request, whatever `storage_integrity.enabled` says. The reason is that `phys` and `hg_*` are addressable when storage integrity is off, and the tenant boundary is the physical database, not the SI contract. Mechanism: the engines take the protected namespace from a new `RewriteTableDynamicArgs.protected_databases` field that housegate always sends, plus the values of `database_map`, so nothing depends on `StorageIntegrityArgs` being present. The V2 catch-all, `SET` refusal and reserved-database semantics are unchanged.
- **T2 — Position-based refusal of identifier parameters.** An `Identifier`-typed query parameter in any database or table position is refused with `InvalidRewriteRequest` and the message `query parameters are not supported in a database or table position`, before any rewrite, in both engines, both SI states. Column-position and value-typed parameters are untouched. Rejected alternative: rewriting `db1.{p}` to `phys.{p}`, which binds any physical table at execution.
- **T3 — Protected names are refused in every position, not double-prefixed.** A database qualifier, `USE` target, `SHOW … FROM` target, table-function argument, table-engine argument or string-lookup argument that names a protected database is refused with `InvalidRewriteRequest` and `protected database <name> is not addressable`. This replaces the harmless-but-nonsensical ``phys.`phys.x` `` rewrite and the `USE phys` pass-through. When the SI surface is active, the existing SI messages for `hg_*` and SI-physical names keep precedence, so no current corpus pin moves.
- **T4 — Sources are rewritten and reported exactly like FROM.** IN operands in every form, `INSERT … SELECT` bodies and `CREATE TABLE … AS SELECT` bodies go through the same table-reference resolution as a FROM reference: a mapped logical table becomes its physical name, an Active SI table becomes the derived safe or unsafe read, and every source appears in `AccessedTables`. This fixes the functional gap (own-table sources that never resolved) and removes the SI-only refusal of `IN <own table>`. Rejected alternative: refusing every IN table operand, which removes a legitimate feature to avoid modelling it.
- **T5 — Allowlists for table functions and table engines.** Every table function that can carry a database or table identity is refused for the caller; a closed list of data-only functions is allowed; the external-data family keeps today's behaviour (non-goal). Every table engine outside a closed list is refused, including engines that take no table argument but persist a data reference (`URL`, `S3`, `File`, …); `Replicated*` engines are allowed only without explicit arguments; `disk` and `storage_policy` table settings are refused. Unknown names are refused. Rejected alternative: resolving `merge('db1', …)` through `database_map`. It is implementable but the argument surfaces (regexes, `currentDatabase()`, heredocs) are exactly where Spec N found lexical bypasses, and no tenant workload needs it.
- **T6 — String-form lookups resolve or refuse.** `joinGet` / `joinGetOrNull` / `dictGet*` / `dictHas` / `dictGetHierarchy` / `dictIsIn` / `dictGetChildren` / `dictGetDescendants` / `hasColumnInTable` are rewritten and reported when their table argument is a string literal that resolves through `database_map` (qualified, or unqualified in the session's logical database) to an ordinary table, and refused otherwise. The emitted string form is whichever form ClickHouse 26.x parses back to the same `StorageID` for a table whose name contains a dot; the implementation plan measures it before the corpus pins it, and if no such form exists these functions are refused outright. An SI table as a lookup target is refused (it is not a safe read).
- **T7 — Every unmodelled statement class is `UnsupportedStatement` in both engines, whatever the SI state.** The native `Success + UNSPECIFIED` pass-through and the C++ `Success + SELECT` fallback both go. `SET` is the one modelled pass-through when the SI surface is inactive (it names no table and clients send it); under V2 it stays refused. `EXPLAIN` is refused in both engines: the native parser preserves it verbatim so its body cannot be rewritten, and an unrewritten body is useless anyway; C++ stops rewriting it, for parity.
- **T8 — housegate fails closed on every rejection.** For every session that reaches the rewriter, a non-`Success` answer is a `RejectedError` and reaches the client as an Exception, with or without storage integrity. The only remaining fail-open is a transport or availability failure (dial, timeout, nil response, closed factory), controlled by a new `rewriter.fail_open_on_unavailable` boolean whose default is `false`; `true` together with `storage_integrity.enabled` is a configuration error. Rejected alternative: keeping `UnsupportedStatement` as a pass-through for "harmless" classes. There is no way to tell a harmless unmodelled statement from `DETACH TABLE phys.`db2.x``.
- **T9 — A lexical guard for ordinary sessions, as defence in depth.** A new `tablerefguard` plugin runs before the rewriter on every ordinary session (not maintenance, not platform-operator, not peer-trusted, not forwarded-from-peer; *amended 2026-10-02 (§14, I1):* forwarded-from-peer sessions are checked at the receiving host) over the surfaces that `sireserved`'s scanner already produces. Its rules are the policy's lexically decidable subset (§9.2), deliberately looser than `sireserved`'s operator rules where a tenant could legitimately trip them. It has an `observe` mode for rollout. It never replaces the engine: an engine that fails the startup probe still refuses startup.
- **T10 — `sitablestate` treats a backslash inside a quoted identifier as unreadable.** `readQuoted` refuses a backslash inside a backtick or double-quoted identifier, so the header becomes unreadable and the existing fail-closed paths fire (`classUnreadable` for a materialized view, "carries data" for `CREATE TABLE … AS`). String literals keep decoding, so `DEFAULT 'a\nb'` in a column definition does not trip it. Rejected alternative: decoding escapes the way ClickHouse does. The decoder would have to match every ClickHouse rule forever; refusing is smaller and the false positive (a governed table whose name needs an escape) is not a real workload.
- **T11 — `hg_promote` joins every reserved list.** `sireserved`, the scrubber and the new guard read `sitable.ReservedDatabases()`; nothing lists the names by hand.
- **T12 — The C++ fixes are parity fixes.** The crash is closed by T2 plus a defensive check that an empty table name never reaches the formatter; `CREATE MATERIALIZED VIEW … TO <Active table>` is refused with the native engine's message; T7 aligns classification. Each is a corpus case or, for the crash, a C++ unit test.
- **T13 — Positive proof at startup, in both SI states.** housegate's behavioural probe runs whenever a rewriter factory exists, not only with storage integrity, and adds policy cases (§9.5). A factory that fails any case refuses startup. This is what makes the new proto field safe: an old engine ignores `protected_databases` and fails the probe.
- **T14 — Every finding is a shared corpus case, and the differential is re-run.** The measured matrix becomes corpus cases with both SI states (`contract_version: V1` with an empty table map is the inactive surface), the existing pins that encode the old behaviour are flipped in the same change, and the Spec N D3 cross-engine differential is executed once more and recorded in this document before either engine is released.

## 5. The table-reference policy

**Names.** A *protected database* is any value of `dynamic_args.database_map`, any entry of `dynamic_args.protected_databases`, and, while the SI surface is active, any database of a `safe_table` / `unsafe_table` and any `reserved_databases` entry. housegate sends `protected_databases = [rewriter.physical_database] ∪ sitable.ReservedDatabases()`. A *mapped* name resolves through `database_map` (qualified, or unqualified through `upstream_logical_database_in_context`). `system` is neither: an allowlisted `system` table resolves to itself in read positions, every other `system` table is refused in every position (§5, "The system database"), and `system` is refused in write and DDL positions as before.

**Positions and outcomes.** Every row applies in both SI states unless it says otherwise.

**Unqualified names that do not resolve.** In dynamic mode, a read-position table name with no database qualifier — `t`, and equally the one-part dotted quoted form `` `db1.t` ``, which ClickHouse parses as a single table name — resolves only through `upstream_logical_database_in_context`. When that context is empty, is not in `database_map`, or maps to a missing remote upstream, the engines refuse the statement with `InvalidRewriteRequest` and `unqualified table "<t>" does not resolve through the session's logical database` (inside an `INSERT … SELECT` / CTAS body the code is `UnsupportedStatement`, as for every embedded-body rejection). They no longer forward it. ClickHouse resolves such a name in the session's current database, which housegate makes the physical database for every session with a non-empty hello database, so a forwarded `` `db1.t` `` reads ``phys.`db1.t` ``, the ordinary physical table of an Active SI table, outside `hg_safe`, and `` `other.x` `` reads another tenant's table. Tenants cannot reach this, because housegate's permission observer refuses the unresolved reference, but the observer is absent on driver sessions (indexer-signed, `IsDriver`, which skip commitgate) and on auth-disabled deployments, so the engines refuse it themselves as defence in depth. A qualified unmapped name (`db2.x`) stays lenient: ClickHouse has no physical `db2`, and the permission observer owns it. In FROM / JOIN a CTE name is not a table reference and is unaffected. An IN operand follows the binding rule below; an operand that is a table reference there is subject to this rule like any other unqualified name. `DESCRIBE`, `EXISTS`, `SHOW CREATE`, `SHOW COLUMNS` and write / DDL targets already refused these names and keep their messages. The table name is inserted verbatim, without escaping a `"` it contains, exactly like the T6 message. When it is the final answer, the rejection carries an empty `table_rewrites` in every statement family, including a write statement's own targets, so no partial map leaks; a refusal that outranks it (the SI write refusal of a view / MV body) keeps exactly the map it would have without the unresolved name.

**Names that bind an unqualified IN operand.** An unqualified IN operand (infix, parenthesised, quoted, tuple, `NOT` / `GLOBAL`, and the `in()` family) is a table reference unless a name ClickHouse binds before any table has the same spelling. Measured on ClickHouse 26.2 under both `enable_analyzer=1` and `enable_analyzer=0` (a tenant chose the analyzer per query or per session, so only a binding that holds under both counted). Amended 2026-10-01 (§13, round 2): that measurement did not cover the old analyzer's rewrites (the EXISTS rewrite that drops a projection alias, name-based WITH propagation under `legacy_column_name_of_tuple_literal = 1`), which read another tenant's table on 25.8 and 26.2; the old analyzer is therefore refused by R5 and the rules below are relied on for the new analyzer only:

- **Bind, operand left unchanged and unreported:** a read-query CTE name, and a WITH expression alias whose value is provably not a table reference — a literal, a tuple or array of literals, a parenthesised function call (a no-parens keyword such as `NOW` or `CURRENT_DATE` is an identifier to ClickHouse, and binds nothing), a scalar subquery (and operators over literals) — in the declaring SELECT and every nested one, even under a same-named table alias; and a projection alias, in its own SELECT only. A stored view body narrows this (below).
- **Do not bind; the operand is a table in the session's logical database, rewritten, reported and SI-checked:**
  - a table-source alias (FROM / JOIN table, subquery, table function): an enclosing SELECT's alias reads the table of that name under both analyzers, and the IN's own SELECT's alias under `enable_analyzer=0`;
  - an enclosing SELECT's projection alias: `enable_analyzer=0` reads the table of that name;
  - a WITH alias whose value is an identifier (bare, quoted, parenthesised, qualified or unresolvable), a no-parens keyword (`CURDATE`, `CURRENT_CATALOG`, `CURRENT_DATE`, `CURRENT_DATETIME`, `CURRENT_ROLE`, `CURRENT_SCHEMA`, `CURRENT_TIME`, `CURRENT_USER`, `GETDATE`, `LOCALTIME`, `LOCALTIMESTAMP`, `NOW`, `PI`, `SESSION_USER`, `SYSDATE`, `SYSDATETIME`, `SYSTEM_USER`, `SYSTIMESTAMP`, `UTC_DATE`, `UTC_TIME`, `UTC_TIMESTAMP`, any case, parenthesised or not), or another alias, so every alias chain: the new analyzer reads the table the identifier names in the same scope (`WITH nosuch AS "other.secret" … a IN "other.secret"` reads `phys."other.secret"`, `WITH "db1.t" AS z … a IN z` the ordinary physical table of Active `db1.t`) and the table named after the alias when nested; the old analyzer substitutes the identifier in a nested scope and reads it. Such an alias also shadows an enclosing binding of its name.

The same holds for a bare keyword written as the operand itself: a no-parens keyword (`a IN NOW`, `a IN (current_user)`) and `EXISTS` / `INTERVAL` in any case (`a IN EXISTS`, `a IN (interval)`), which Polyglot parses as a bare identifier. ClickHouse reads the table of that name in the current database under both analyzers, so each is an unqualified table operand like `a IN b`: rewritten, reported, and refused in a position no rewrite reaches (R2).

**Stored view bodies.** Inside a `CREATE VIEW` or `CREATE MATERIALIZED VIEW` body (with `TO`, `ENGINE`, `POPULATE` or `REFRESH`), at the body's own level and in every nested query, the binding is narrower than in a plain SELECT. Measured on ClickHouse 26.2 and 25.8 under both analyzers:

- **Bind:** a read-query CTE name, and a WITH alias whose value is a single folded literal — a number (decimal, hex `0x…`, binary `0b…`, `inf`, `nan`; negated or not), a string (quoted, `x'…'`, heredoc `$$…$$`), NULL or a boolean, optionally parenthesised, or a flat tuple or bracket array of those (`(1, 2)`, `[-1, 2]`).
- **Do not bind** (ClickHouse reads the table named after the alias): a WITH alias with any other value — a function call, parenthesised or not, a cast, an operator (`1 + 1`), a scalar subquery, `tuple(…)` / `array(…)`, a parenthesised or nested tuple, an array of tuples — and every projection alias, whatever its value. Before this rule, ``CREATE VIEW db1.vv AS WITH (SELECT 1) AS `db2.my-t` SELECT … WHERE v IN `db2.my-t` `` read ``phys.`db2.my-t` ``.

The rule covers every query of the body, including a root or nested set operation (`UNION` / `INTERSECT` / `EXCEPT`, parenthesised or not, the operand in either branch). A top-level `view()` table function and `INSERT … SELECT` / `CREATE TABLE … AS SELECT` bodies follow the plain-SELECT rule above (measured); a `view()` inside a stored view body follows the stored rule. In both rules an unquoted `inf` / `nan` (any case) or `0b…` binary number is a literal to ClickHouse and binds. Known Polyglot divergences, which can only turn a name or a syntax error into a constant (measured: no table read), and are therefore not "measured to bind": `0x_10` is an identifier to ClickHouse but a `hex_number` to Polyglot (regenerated as `0x10`); `$é$x$é$` is a ClickHouse syntax error that Polyglot regenerates as `'x'`; `x'41''42'` is a ClickHouse syntax error that Polyglot regenerates as `x'41'42'`.

Because the current database is the physical one, forwarding such an operand read another tenant's table or the ordinary physical table of an Active SI table, unreported. The cost is that a same-scope `a IN o1` with `o1` a table alias, or a nested `a IN z` with `z` an outer projection alias, which the new analyzer binds to the alias, now reads the table of that name (normally an unknown-table error).

*Precedence of this rule.* It sits at the ordinary-rewrite step of the precedence below, inside the SELECT walker, after every other check that can fire on the same statement: T2, T7, T3, T5 (with the SI surface active, inside the SI handlers), T6, R5 and R2; every SI read-surface refusal (the SI namespace policy, the SI physical-table and unauthorized-logical checks, FINAL / SAMPLE / PREWHERE / WITH OFFSET / reserved-column refusals, and an SI derived-read error, which wins even when its table comes later in walk order); and, for a view / MV body that reads an authorized SI table, the SI write refusal. A write statement's own targets are resolved first and refused with their own messages. For an unqualified IN operand under an active SI surface, the SI namespace refusal fires first only when the session's execution database cannot be resolved (no `upstream_physical_database_in_context` and no resolvable logical context); housegate always sends the physical context for a session with a hello database, so there the unresolved-name refusal is what fires. When several names are unresolved, the first in document order is named: `FROM b JOIN a` names `b`, a FROM subquery precedes a later JOIN, a select-list subquery precedes FROM, a CTE body precedes the main query, and FROM precedes WHERE / IN.

**The system database (step 1).** Every tenant reaches ClickHouse as one shared user, so ClickHouse's own per-user filtering of `system.*` filters nothing between tenants (the survey measured another tenant's query text, query_id, table and column names, partition values, mutation commands, merges and dictionaries on 26.2 and 25.8). Both engines therefore apply an allowlist to caller input, in dynamic mode and both SI states:

- *Allowed, unchanged behaviour:* the class (b) static / server-global tables (`aggregate_function_combinators`, `azure_queue_settings`, `build_options`, `codecs`, `collations`, `contributors`, `dashboards`, `data_type_families`, `database_engines`, `formats`, `functions`, `jemalloc_bins`, `jemalloc_stats`, `keywords`, `licenses`, `merge_tree_settings`, `numbers`, `numbers_mt`, `one`, `primes`, `privileges`, `replicated_merge_tree_settings`, `s3_queue_settings`, `settings`, `settings_changes`, `table_engines`, `table_functions`, `time_zones`, `tokenizers`, `unicode`, `warnings`, `zeros`, `zeros_mt`), `clusters`, and the class (c) tables the Sentio driver and clients read by physical name: `tables`, `columns`, `data_skipping_indices`, `projections`, `parts`, `parts_columns`, `projection_parts`, `projection_parts_columns`, `databases`, `completions`, `mutations`. The `information_schema` / `INFORMATION_SCHEMA` databases are not checked.
- *Refused,* `UnsupportedStatement` with `system table system.<t> is not accessible`: every other `system` table — class (a), class (b\*), the class (c) tables nobody consumes (`detached_parts`, `rocksdb`, `iceberg_history`, `database_replicas`, `dropped_tables`, `dropped_tables_parts`, `detached_tables`) and any name not on the list, so a table a future ClickHouse release adds is refused by default. The message names the table after ClickHouse's identifier decoding (a `merge()` / `Merge` pattern verbatim), and the refusal reports it in `original_accessed_tables`.
- *Positions:* every caller-input reference, in every position of the table above, including table-function and table-engine arguments (a pattern or any non-static table argument is never an allowlist match), string-lookup arguments, opaque ALTER / INSERT query text, every qualified `system.<name>` in a command's text (DESCRIBE, EXISTS, SHOW CREATE, SHOW COLUMNS / INDEX, RENAME, GRANT, ALTER … UPDATE), the two-clause `SHOW COLUMNS FROM t FROM system`, and an unqualified name while the session's logical database is `system`. A SHOW COLUMNS / INDEX target of three or more parts is read the way ClickHouse's parser reads it — `name_parts[0]` is the database and `shortName()`, the last part, is the table (measured on 26.2 and 25.8: `SHOW COLUMNS FROM system.tables.processes` lists `system.processes`) — so a refused last part is refused with the system-table message. In command text, where the engine cannot tell a SHOW target from an expression, a run of three or more parts is checked both as (first, last) and as (first, second). The native engine additionally refuses every remaining three-or-more-part SHOW COLUMNS / INDEX target with `statement is not supported` (engine-local: ClickHouse's parser keeps no part count, so rewriter-grpc cannot see it; the native engine used to echo `SHOW COLUMNS FROM db2.x.y` unreported). SQL the engine itself emits (the SHOW TABLES `system.tables` synthesis, the SI DESCRIBE over `system.columns`) is output, not input, and is never checked.
- *Spelling:* names are compared the way ClickHouse's lexer and ParserIdentifier read them, for every identifier quoting: bare, backticks and double quotes with backslash escapes decoded, and Unicode `“…”` with its body verbatim (measured on 26.2: `DESCRIBE “system”.“processes”` lists `system.processes`); a `‘…’` lexeme is a string, never a name (`` `sys\x74em`.`\x70rocesses` `` and `` `system\N`.processes `` both read `system.processes`, measured on 26.2). ClickHouse database and table names are case-sensitive (measured on 26.2: `SYSTEM.processes` is `UNKNOWN_DATABASE`, `system.Tables` is `UNKNOWN_TABLE`), so the database must be exactly `system` and a table matches only an exact allowlist entry.
- *SHOW forms that read a refused table are refused with the table they read:* `SHOW PROCESSLIST` (`processes`), `SHOW MERGES` (`merges`), every `SHOW DICTIONARIES` form (`dictionaries`), `SHOW USERS` / `ACCESS` (`users`), `SHOW ROLES` (`roles`), `SHOW CURRENT ROLES` (`current_roles`), `SHOW ENABLED ROLES` (`enabled_roles`), `SHOW GRANTS` (`grants`), `SHOW [SETTINGS] PROFILES` (`settings_profiles`), `SHOW [ROW] POLICIES` (`row_policies`), `SHOW [CURRENT] QUOTA` (`quota_usage`), `SHOW QUOTAS` (`quotas`), `SHOW FILESYSTEM CACHES` (`filesystem_cache_settings`). `SHOW CREATE USER / ROLE / QUOTA / ROW POLICY / SETTINGS PROFILE / DICTIONARY` stay refused as before. Kept: `SHOW CLUSTER[S]`, `SHOW SETTINGS [LIKE]`, `SHOW FUNCTIONS`, `SHOW ENGINES`, and, with the SI surface inactive, `SHOW CHANGED SETTINGS`, `SHOW SETTING`, `SHOW PRIVILEGES`. The native engine also refuses, with `statement is not supported`, a SHOW kind in neither list while the surface is inactive (an engine-local rule: ClickHouse's parser rejects an unknown kind, so rewriter-grpc never sees one). A SHOW form's own SI namespace check and its body check (`WHERE` / `LIMIT` subqueries) run first.
- *Precedence:* right after T3 and before T5 / T6 / R5 / R2 and the handlers. While the SI surface is active and the statement also names a storage-integrity object (an SI physical or reserved database, an Active SI table, or an SI logical database through a pattern carrier), the check is deferred as a whole: every later rule answers first — T6 and the command-text findings in the preflight, T5 / R5 / R2 inside the SI handlers, the SI namespace, physical-table and write refusals, and every other handler refusal — and the engine runs the system-table check only on the pipeline's would-be `Success`, before the mid-statement drop gate (pinned: `SELECT joinGet('db1.o', 'a', 1) FROM db1.t JOIN system.processes USING (a)` answers the T6 message, a `mysql(…)` join the T5 message, `SETTINGS additional_result_filter = '1'` the R5 message, each only under V2); so `SELECT * FROM hg_safe.db1__t JOIN system.processes` keeps the SI physical-table message and `CREATE VIEW db1.v AS SELECT * FROM db1.t JOIN system.processes` keeps the SI write message, while `SELECT * FROM db1.t JOIN system.processes` is refused as a system-table read. When several refused system tables are named, the message names the first in collector order, which both engines must reproduce: for a structured statement its own write / DDL targets, then read sources and carriers in walker order (a CTE body before the main query, the select list before FROM, FROM / JOIN before WHERE / IN, a FROM subquery before a later JOIN), then opaque texts, then string-lookup arguments — so `SELECT dictGet('system.aaa', 'x', 1) FROM system.processes` names `processes` and `INSERT INTO system.query_log SELECT * FROM system.processes` names `query_log`; for a command node, its qualified names in text order, then its SHOW COLUMNS / INDEX target, then its unqualified target.
- *Known residual until step 2:* the allowed class (c) tables are still forwarded verbatim, so a tenant still sees every tenant's table and column names, index and projection expressions, `parts*` partition values and — through `mutations` — another tenant's mutation command text, including its `WHERE` literals. They stay passthrough because the Sentio driver reads them by physical name (`database = <physical> AND name LIKE '<logical>.%'`) and refusing them stops processors from starting (and hangs `waitMutations`). Step 2, a follow-up issue, serves them as a filtered logical rewrite (the `SHOW TABLES` pattern: filter to the caller's logical databases, project logical names back, rewrite `create_table_query` / `engine_full` / `as_select`) together with the sentio-core `chx` change to logical names, shipped in lockstep.
- *housegate (step 2, housegate/housegate#218):* `PermissionCommitGateObserver.checkAccess`'s blanket `system` read exemption ([pkg/network/permission_commitgate_observer.go](../../../pkg/network/permission_commitgate_observer.go)) must narrow to the same allowlist, as defence in depth, and its comment, which says per-row visibility is enforced server-side, must be corrected. It must not become a ClickHouse `REVOKE` on the shared user: the relay's legacy completion probe reads `system.processes` with the session's own login, and the metrics collector and SI guards read `system` over the same credentials. Amended 2026-10-01 (§14, D5): this narrowing was planned for Plan C but moved to step 2 by the 2026-09-30 user ruling ("分两步"); Plan C ships without it, so until #218 lands the engines' allowlist is the only `system` read check.

**Table functions (T5).** Refused, with `UnsupportedStatement` and `table function <name> is not accepted`: `merge`, `remote`, `remoteSecure`, `cluster`, `clusterAllReplicas`, `loop`, `dictionary`, `mergeTreeIndex`, `mergeTreeProjection`, every name starting with `mergeTree`, `timeSeriesData`, `timeSeriesTags`, `timeSeriesMetrics`, `timeSeriesSelector`, `prometheusQuery`, `prometheusQueryRange`, `clickhouse`, `mysql`, `postgresql`, `mongodb`, `jdbc`, `odbc`, `executable`, `fuzzQuery`, `fuzzJSON`. Allowed, walked for their bodies where they have one, never reported: `numbers`, `numbers_mt`, `generate_series`, `generateSeries`, `generateRandom`, `zeros`, `zeros_mt`, `null`, `values`, `format`, `input`, `view`. Non-goal, unchanged: `url`, `s3`, `gcs`, `oss`, `cosn`, `file`, `hdfs`, `azureBlobStorage`, `iceberg`, `deltaLake`, `hudi`, their `*Cluster` forms, `sqlite`, `redis`. Any other name is refused with `table function <name> is not recognised`. `INSERT INTO FUNCTION …` and `CREATE TABLE … AS <function>(…)` stay refused as today. The names are matched case-insensitively, as ClickHouse resolves them.

**Table engines (T5).** Allowed: `MergeTree`, `ReplacingMergeTree`, `SummingMergeTree`, `AggregatingMergeTree`, `CollapsingMergeTree`, `VersionedCollapsingMergeTree`, `GraphiteMergeTree`, their `Replicated` forms only when written without arguments (macro-derived paths), `Memory`, `Log`, `TinyLog`, `StripeLog`, `Null`, `Set`, `Join`, `View`, `MaterializedView`, `LiveView`. Everything else is refused with `UnsupportedStatement` and `table engine <name> is not accepted`; this includes `Merge`, `Buffer`, `Distributed`, `Dictionary`, `URL`, `S3`, `File`, `HDFS`, `AzureBlobStorage`, `Iceberg`, `DeltaLake`, `Hudi`, `MySQL`, `PostgreSQL`, `MongoDB`, `SQLite`, `Redis`, `JDBC`, `ODBC`, `ExternalDistributed`, `Kafka`, `RabbitMQ`, `NATS`, `FileLog`, `Executable`, `ExecutablePool`, `KeeperMap`, `EmbeddedRocksDB`, `TimeSeries`. A `CREATE TABLE` or `ALTER TABLE … MODIFY SETTING` that sets `disk` or `storage_policy` is refused with `table setting <name> is not accepted`. `CREATE DICTIONARY` stays `UnsupportedStatement`, now fail-closed in housegate.

**Precedence.** A statement is examined in this order, and the first rule that fires names the outcome: parameter in a table position (T2); unmodelled class (T7); protected database in any position (T3, with the SI messages first while the surface is active); a `system` table outside the allowlist ("The system database" above; while the surface is active and the statement names an SI object, deferred behind every later rule to the would-be `Success`); table function / engine / setting not allowed (T5); unresolvable string lookup (T6); then the ordinary rewrite. Both engines follow the same order so the corpus can pin one message per case. Command-text statements (`EXPLAIN`, `DETACH`, `OPTIMIZE`, `SYSTEM`, …) run the parameter scan over their whole text before the class refusal, so a `{p:Identifier}` anywhere in them names the outcome, and an unmodelled class is refused before its protected names are examined. While the SI surface is active, every unmodelled class is answered with the SI catch-all message the engines already return for `CHECK TABLE` / `SYSTEM` under contract V2; `statement is not supported` is the inactive-surface text.

**Mutation expressions, column expressions and settings values.** A subquery, a table-operand `IN` or a table function inside a structured `UPDATE` / `DELETE` predicate, an `ALTER … DELETE` predicate or a column expression (`DEFAULT` / `MATERIALIZED` / `ALIAS` / `EPHEMERAL`, `TTL`, `PARTITION BY`, `ORDER BY`, `SAMPLE BY`, `CONSTRAINT`, `INDEX`) is rewritten and reported like any other read source where the engine models the position and refused with `statement is not supported` where it does not; it is never forwarded unchanged. An opaque `ALTER TABLE … UPDATE` / multi-command tail, `MODIFY TTL … WHERE` or `MODIFY COLUMN … DEFAULT` action is scanned with the raw tokenizer and refused when it carries a subquery, a table-operand `IN` or a parameter (the parameter and protected messages keep precedence). `ALTER TABLE … MODIFY QUERY` is handled like a materialized-view body or refused; `FETCH PARTITION|PART`, `ATTACH PARTITION|PART … FROM`, `REPLACE PARTITION … FROM` and `MOVE PARTITION … TO TABLE` are refused in dynamic mode. A materialized view's own `ENGINE` / `SETTINGS` follow the T5 allowlist exactly like `CREATE TABLE`. Settings whose value is SQL evaluated against tables — `additional_table_filters`, `additional_result_filter`, `parallel_replicas_custom_key` — and settings that change how ClickHouse parses later statements — `dialect`, `polyglot_dialect`, `allow_experimental_polyglot_dialect`, `allow_experimental_prql_dialect`, `allow_experimental_kusto_dialect`, any name ending in `_dialect` — and settings that change what a name binds to — `enable_global_with_statement` (at `0`, ClickHouse stops carrying a WITH alias or CTE name into nested queries and later set arms and reads the table of that name there, in a query, a view body and a view created under a session `SET`) `compatibility` (the versions 20.1, 20.8 and 21.1 restore `enable_global_with_statement = 0` as the default and read the same tables; any version changes a group of defaults nobody measured) `implicit_table_at_top_level` (its value names the table a FROM-less `SELECT` reads), and, as defence in depth behind the refused `promql` dialect, `promql_table` / `promql_database` — are refused with `table setting <name> is not accepted`, whatever the value, in a query-level `SETTINGS` clause (a view or materialized-view body's included) and in a session `SET`. The name-resolution list was measured on ClickHouse 26.2 and 25.8 under both analyzers by flipping every Bool setting (802 / 711) and eleven `compatibility` versions over the binding shapes; only `enable_global_with_statement = 0` and the `compatibility` versions that restore it turned a trusted name into a table read. `enable_analyzer` / `allow_experimental_analyzer` were accepted on the grounds that every binding rule in this section was measured under both analyzers; amended 2026-10-01 (§13, round 2): they are refused unless the value is a true literal, and `legacy_column_name_of_tuple_literal` and `profile` are refused whatever the value, because the old analyzer's rewrites read tables the binding rules trust. HouseGate's Query-packet check and the C++ engine refuse the same names. Where the engine forwards setting text verbatim — a session `SET`, the opaque text after an `INSERT` column list, a command's `SETTINGS` tail — a setting name whose source spelling is not its plain text (a backslash escape, or a doubled quote inside a quoted name) is refused with `statement is not supported`: ClickHouse decodes `\N` to nothing, so `` `\Nenable_global_with_statement` `` and `` `enable\N_global_with_statement` `` name the refused setting, and the engine cannot model every escape ClickHouse decodes. Structured positions are regenerated with the escape preserved and ClickHouse answers `UNKNOWN_SETTING`. Such a verbatim path fails closed on any `SETTINGS` clause or `SET` list it cannot fully parse into verbatim-safe `name = value` pairs — never skips it: a `SETTINGS` keyword ending the text, or followed by a setting name that does not start a parseable top-level assignment list (only a `SHOW [CHANGED] SETTINGS` statement, with `SHOW` as its first token and no assignment list after `SETTINGS`, is exempt — not a column or alias named `show` in front of a real clause — and a `SETTINGS` word not followed by a name, such as a column in `UPDATE settings = 1`, is not a clause), and a compound (dotted) setting name such as `SQL_a.b` or `` `SQL_a`.b ``, which ClickHouse accepts as a custom setting, are refused with `statement is not supported` (a deliberate over-refusal; HouseGate's own `SQL_x_*` / `SQL_sentio_*` keys contain no dot). As a backstop, a quoted name with an escape or a doubled quote followed by `=` anywhere after a `SETTINGS` keyword (or the `SETTING` keyword of `ALTER … MODIFY SETTING`) is refused the same way. The table-setting paths follow the same rule: an `ALTER … MODIFY SETTING` / `RESET SETTING` key list, forwarded verbatim, is refused unless it parses into verbatim-safe, undotted names, because ClickHouse decodes `` `\Nstorage_policy` `` to the refused `storage_policy`; the session-`SET` carve-out admits only `<name> = <literal or bare identifier>` assignments. The same settings can arrive in the native-protocol Query packet without passing through the rewriter, so HouseGate refuses them on ordinary sessions (Plan C). A `SHOW COLUMNS` / `SHOW INDEX` `WHERE` / `LIKE` body that carries a subquery, a call, a table-operand `IN`, a parameter or a protected qualifier is refused (parameter and protected messages first, then `statement is not supported`). In dynamic mode every engine-internal error (an unmodelled AST shape, a generator limit) is a coded `UnsupportedStatement` / `statement is not supported` rejection in both surfaces, never a transport error the proxy could fall open on.

**What the engines report.** A `Success` answer lists every table the statement can read or write, each with its `logical_database` / `physical_database` / `is_storage_integrity`, in a stable order: for a write statement the target comes first; the sources, and every entry of a SELECT-family statement, follow in the engines' key-sorted collector order (sorted by the original database and table as written), which both engines produce identically so the corpus can pin one order. A bare-identifier IN operand (`a IN b`, `a IN (b)`) is treated as a table in the session's logical database even though ClickHouse resolves a same-named column first: the table reading is the fail-safe one (it can only reach the tenant's own governed table) and the engines cannot see column names. `AccessedTables` on a rejection may still be partial, as today.

### 9.2 The `tablerefguard` plugin

`sireserved`'s scanner (`scanSQLSurfaces`, the literal, heredoc, comment and quoted-identifier consumers, `identifiers`) moves unchanged into a leaf package `pkg/sqlsurface`; `sireserved` keeps its rules and behaviour over the moved scanner. The new `pkg/plugins/tablerefguard` plugin is a `QueryPlugin` with `RunOnForward() == true` and `RunOnPeerTrust() == true`, registered in `buildServer` right after `sireserved` whenever a rewriter is configured, so it runs on the original SQL before `forward` and `rewrite`. *Amended 2026-10-01 (§14):* it is wired on every server that forwards to ClickHouse (a `shard`, an `upstream` or a host-injected cluster), after `auth` / `usage` (and `sireserved` when storage integrity is enabled) and before `concurrency`, `forward` and `rewrite`, whether or not a rewriter was built: under `rewriter.fail_open_on_unavailable` a server that could not build its rewriter keeps the guard as its only policy layer. Router-only servers forward whole sessions to peers and get none. `buildServer` warns at startup when `rewriter.physical_database` is empty, because G2 is then inactive. It returns immediately on maintenance, platform-operator, peer-trusted and forwarded-from-peer sessions; driver sessions are ordinary. *Amended 2026-10-02 (§14, I1):* it runs on forwarded-from-peer sessions, against the receiving host's physical database, like `rewrite` and the Query-packet check: the host owns their original client SQL, and an origin that is a router-only server runs no guard, so skipping them left a forward-pivoted session unchecked at both ends. Only `remote()` peer-trusted loopbacks are skipped. Configuration: `PhysicalDatabase` (from `rewriter.physical_database`), `ReservedDatabases` (`sitable.ReservedDatabases()`), `Mode` (`enforce` default, or `observe`). Rules, each named in the error and in a `clickhouse_proxy_tableref_guard_rejections_total{rule}` counter:

- **G1 reserved names.** Any identifier-boundary token equal to a reserved database on the with-literals surface: refuse. Same rule as `sireserved`, because a tenant never has a reason to mention them, including in a string literal. Compared case-insensitively.
- **G2 physical database.** On the outside-literals surface, refuse the physical database name when it is a qualifier (`phys.`, `` `phys`. ``, `"phys".`), the object of `USE`, or the `FROM` / `IN` object of a `SHOW` statement; and, inside the parenthesised argument list of a carrier or lookup callable (G3's list plus the T6 list), refuse it as a bare identifier or as a string literal, including a literal that names it as a `phys.` prefix. Elsewhere the name is allowed, because a column or alias may share it, and `DEFAULT` shows why a bare-token rule would be wrong when the physical database is called `default`. *Amended 2026-10-01 (§14):* G2 also refuses the physical database as the object of `DATABASE` (`CREATE` / `DROP` / `ATTACH` / `DETACH` / `ALTER` / `TRUNCATE` / `EXISTS` / `DESCRIBE` / `SHOW CREATE … DATABASE [IF [NOT] EXISTS] phys`, `SYSTEM … DATABASE [REPLICA] phys`), as any name of a `RENAME`, `EXCHANGE`, `BACKUP` or `RESTORE` statement that names a `DATABASE` (`RESTORE DATABASE x AS phys`), and as the object of `TABLES FROM | IN [IF EXISTS]` in any statement (`TRUNCATE [ALL] TABLES FROM phys`, `SHOW TABLES FROM phys`). The engines already refuse these under T3; the guard positions were checked with `clickhouse format` on 26.8.1 against a list of database-object statements, which is not a completeness proof. The name is matched case-sensitively, as ClickHouse matches database names. A tuple element such as `phys.1` and a column named `database` aliased as the physical database (`SELECT database phys`) are refused too: known, safe false refusals.
- **G3 carrier callables.** A call to any name on §5's refused table-function list: refuse. This mirrors T5 exactly, so it adds no false positive beyond the policy. *Amended 2026-10-01 (§14):* "Exactly" covers every T5 refusal the guard can see lexically: the "not accepted" table functions (every name starting with `mergeTree` except the ordinary function `mergeTreePartInfo`), the ClickHouse 26.8.1 table functions on none of T5's three lists that the engines refuse as "not recognised" (none shares a name with an ordinary function), and an `ENGINE` clause of a `CREATE` / `REPLACE` / `ATTACH` `TABLE` or `VIEW` whose engine is outside T5's allowlist (case-sensitive, `Replicated*` only without arguments; `Buffer`, `Distributed`, `Merge`, `TimeSeries`, … are refused). A name is a call only when it is followed by `(` and is not in a name position: after `.`, after `INTO` / `TO` / `INDEX` / `PROJECTION` / `DATABASE`, after `TABLE` / `VIEW` / `DICTIONARY` in a `CREATE` / `ATTACH` / `REPLACE` / `TEMPORARY` / `INTO` header, or as the `ENGINE` name (measured on 26.8.1: a table function there is a syntax error, so `INSERT INTO db1.cluster (a) …` and ``CREATE TABLE db1.`Merge` (…)`` are tables with column lists). `INSERT INTO [TABLE] FUNCTION f(…)`, `DESC[RIBE] [TABLE] f(…)`, `FROM` / `JOIN` and every expression position stay calls. G3 is checked before G2, so `merge('phys', …)` is attributed to the carrier.
- **G4 identifier placeholders.** Any `{name:Identifier}` placeholder: refuse. This is position-blind and therefore wider than T2 (a column-position `Identifier` parameter is refused too). It is deliberate: the guard has no grammar, an `Identifier` parameter has no legitimate table-free use that a tenant workload needs, and `sireserved` already applies it to operators. It is the one rule `observe` mode exists to measure.
- **G5 escaped identifiers.** A backslash inside a backtick or double-quoted identifier: refuse. Backslashes inside string literals are allowed. *Amended 2026-10-01 (§14):* they are decoded, not left raw: a single-quoted literal is compared (G1, and G2 inside carrier and lookup arguments) as the value ClickHouse reads, because ClickHouse decodes it before `joinGet` / `dictGet` read it as a table name (measured on 26.8.1: `joinGet('\x70hys.j', …)` reads `phys.j`). A `\x` escape without two hex digits is refused under `scan`; a heredoc body stays raw, as in ClickHouse.
- Heredocs and comments follow Spec N D1: a heredoc body is blanked from the outside surface and kept on the literal surface; a `$` that opens no heredoc is refused. *Amended 2026-10-01 (§14, D7):* a statement the lexical model cannot scan is refused and counted under a sixth label, `scan`: a `$` that opens no heredoc or directly follows an identifier byte (`x$$` is one identifier), a `#` that opens no comment (only `# ` and `#!` do; a line comment ends only at `\n`), an unterminated quote, comment or heredoc, an undecodable `\x` escape, and any byte ≥ 0x80 outside a quoted identifier, string literal, comment or heredoc body (ClickHouse reads Unicode whitespace there as a separator). The last includes a leading UTF-8 byte-order mark, which ClickHouse accepts: a known, safe false refusal.

`observe` logs and counts instead of refusing. The error shape is `sireserved`'s (a plugin error, relay default code), with the message `table-reference guard: <rule>: <detail>; the rewriter applies the same policy`.

### 9.7 Query-packet settings

The native protocol carries per-query settings in the Query packet, outside the SQL text, so neither engine sees them. HouseGate refuses, before forwarding and in every session kind the engines would govern, a Query-packet setting that §5 R5 refuses in SQL, with the same name and value rules: the R5 list including the name-binding settings (`enable_global_with_statement`, `compatibility`, `implicit_table_at_top_level`, `promql_table`, `promql_database`), `legacy_column_name_of_tuple_literal` and `profile` whatever the value, and `enable_analyzer` / `allow_experimental_analyzer` unless the value is literal true (§13 round 2). Setting names arrive decoded, so the escaped-spelling rule does not apply here. Deployments keep the analyzer on in every ClickHouse settings profile a tenant session can use; the engines and HouseGate cannot see a user's default profile. The refusal reaches the client as an Exception naming the setting. *Amended 2026-10-01 (§14):* the check is `pkg/plugins/querysettings`, wired with the guard on every server that forwards to ClickHouse. It has no `observe` mode (D6). It skips maintenance, platform-operator and `remote()` peer-trusted sessions and runs on ordinary, driver, origin-side forwarding and forwarded-from-peer sessions; names are compared case-insensitively, and a true value is exactly `1`, `true`, `'1'` or `'true'` in any case, compared verbatim. A pre-54429 Query packet carries its settings in the old format, whose decoding is not proven against a hostile client, so any old-format setting is refused on a governed session whatever its name or value. The Exception reads `table setting <name> is not accepted (native-protocol query setting)` (a plugin error, relay default code 403) and the session stays usable. Every refusal is logged at warn level (setting, reason, query id, connection, account, user) and counted in `clickhouse_proxy_query_settings_rejections_total{setting}`, whose label is the lowercased fixed name, `other_dialect` for a `_dialect` suffix match, or `old_format`, so the label set stays bounded.

### 9.8 Sessions whose hello database is the physical database

*Amended 2026-10-02 (§14, C1).* A ClientHello database equal to `rewriter.physical_database` is not a logical database. The Sentio indexer driver connects this way through its agent sidecar (production `charts/sentio-node`: `housegate_dsn` ends in `/<physicalDatabase>`), and `forward.Plugin` already short-circuits the name for internal services. `sessionstate.OnHello` therefore records no logical database for it, and every rewriter request on such a session carries an empty `upstream_logical_database_in_context` while `protected_databases` still lists the physical database and `upstream_physical_database_in_context` still names it. Recording it would make the logical context a protected database, which both v0.16.0 engines refuse for every statement under T3. With the empty context, qualified logical names rewrite, allowlisted `system` reads that bind the physical name as a string literal pass, and an unqualified name is refused under §5's unresolved-name rule. The guard and the Query-packet check apply as on any driver session.

## 12. Risks

- **Legitimate tenant SQL that the policy now refuses.** Table functions on own tables (`merge('db1', …)`), engine-level references (`Buffer`, `Distributed`), `EXPLAIN`, `SET` under V2, `Replicated*` with explicit paths, `Identifier` parameters. Each is a deliberate decision in §4 with the reason recorded; the observe-mode counters and the devnet2 cycle are the detection mechanism, and the corpus makes any later widening an explicit act.
- **Driver traffic.** sentio's indexer driver is an ordinary session for the rewriter and the guard. Its traffic is logical DDL and INSERTs today; the devnet2 cycle and the integration case in §10.4 are the check. If it needs a refused shape, the fix is a driver-side change, not a policy hole.
- **Fail-closed on transport failure by default.** A rewriter outage now stops ordinary traffic instead of forwarding unrewritten SQL that would have failed on ClickHouse anyway. Operators who prefer availability set `fail_open_on_unavailable` while storage integrity is disabled.
- **Engine parity.** Two implementations of one policy will drift; the corpus and the differential run are the only things that keep them equal, and the C++ side is testable only on the build box. The paired-PR discipline of Spec N is kept.
- **T6 depends on a ClickHouse parsing fact** (the string form of a dotted table name in `joinGet` / `dictGet`). The plan measures it first; the fallback is to refuse the functions, which is what the guard already does for a physical-name argument.
- **The guard is lexical.** It refuses what it can see and defers the rest to the engine; a bypass of the guard is not a bypass of the policy. Conversely G4 and G5 refuse some SQL the engine would accept; that is the price of not modelling grammar in the proxy, and `observe` mode measures it.
- **Non-goals remain open.** `url` / `s3` / `file` are unchanged and tracked separately on the ClickHouse user side; the class (c) `system` tables the Sentio driver reads (`tables`, `columns`, `parts*`, `mutations`, …) stay passthrough until step 2 (§5, "The system database"). This document records them so the gaps are not rediscovered.

## 13. Amendment 2026-10-01: table-engine arguments and `DEPENDS ON`

**Finding.** rewriter-go v0.15.0 answered `Success` for a read inside the arguments of an allowed table engine and forwarded it unrewritten and unreported, because only the T5 allowlist looked at an `ENGINE` clause, and it forwarded `ALTER … MODIFY REFRESH … DEPENDS ON <name>` verbatim. rewriter-grpc already refused both (engine-cpp-v2 task I3, ledger lines 12 and 13). Measured on ClickHouse 25.8: with `allow_deprecated_syntax_for_merge_tree = 1` (a session `SET`, or the `CREATE` statement's own `SETTINGS` clause) the deprecated positional signature of every MergeTree-family engine evaluates a subquery in its key or sampling slot at `CREATE` time, and `MergeTree(d, (SELECT throwIf(n = 42, 'LEAK') FROM phys.`db2.x`), 8192)` raised another tenant's row. 26.2 refuses a subquery in a key (`Key expressions cannot contain subqueries`) but accepts an IN-table key (`n IN phys.`db2.x``). The refused engines evaluate subqueries in their arguments on both versions (Distributed sharding key, Merge regexp, URL / File format, GenerateRandom, KeeperMap). `DEPENDS ON` names are stored verbatim, an unqualified one resolves in the view's own (physical) database, and no name is checked for existence.

**Rule (T5, R2).** Every table-engine argument is a governed expression position, in both SI states and every `ENGINE` clause (`CREATE TABLE`, a materialized view's inner engine, CTAS, a clone `AS <table> ENGINE = …`): a read there is answered exactly as the same read in a column `DEFAULT` (T2, T3 or the SI physical-table message, the system-table refusal, a table-function T5 refusal, T6, the SI namespace messages, otherwise R2 `statement is not supported`); a read-free argument is unchanged. T5 still judges the engine's name, so a refused engine stays refused; an argument that names a protected database, a system table or a parameter may now be answered by that earlier rule instead of the engine refusal. The table-engine row of §5 therefore reads "refuse" for every column whatever the engine. A `REFRESH … DEPENDS ON` clause in opaque `ALTER` text is refused with R2 `statement is not supported` (a parameter, protected or system name keeps its earlier message); its names are refused rather than resolved because no engine lets a tenant create a refreshable view (`CREATE … REFRESH` is refused), so a resolved dependency could only name a view the tenant does not own. `allow_deprecated_syntax_for_merge_tree` is not added to the R5 list: once every argument is governed it only selects how governed expressions are parsed, and adding it would widen the cross-engine and HouseGate Query-packet contract with no read left to close.

**Pins.** rewriter-go `native_engine_args_test.go` (metamorphic against a column `DEFAULT`, every allowed engine, both SI states) and twelve shared corpus cases `si_tr_engine_arg_{phys,logical,hg_safe}_subquery{,_v2}_rejected` and `si_tr_depends_on_{logical,unqualified,phys}{,_v2}_rejected`, whose outcomes match what rewriter-grpc pins for the same positions (`TableRefFidelity.EngineArgumentsAreGoverned`, `ModifyRefreshDependsOnIsGoverned`); the byte-identical corpus copy and a C++ run of the new cases are still owed in the paired rewriter-grpc change.

**Fix round 1 (review of 4f22a4d).** *Nested EXPLAIN:* an `EXPLAIN` statement of any kind nested in another statement, in any expression position, is refused fail-closed (rewriter-go: `statement is not supported`, the SI catch-all with the surface active; the walk refuses before T3 can name a protected database inside it). ClickHouse 25.8 rewrites `(EXPLAIN …)` to `SELECT * FROM viewExplain(…)` and starts executing it over the named table in an ENGINE argument, PARTITION BY or ORDER BY; the pinned Polyglot keeps it as an opaque command node no collector can see into. The messages are engine-local (rewriter-grpc sees the `viewExplain` rewrite ClickHouse's parser produces), so no corpus case pins them. *Column data types and CODECs:* a read-bearing expression inside a data-type parameter or a CODEC argument is refused fail-closed; ClickHouse rejects a query there before evaluation (both versions). A table `SETTINGS` value is a storage expression and follows the column-`DEFAULT` rule.

**Round 2 (user ruling 2026-10-01): the old analyzer is refused.** rewriter-grpc's I3 review (C2, C3) reproduced on 25.8 and 26.2 two reads that both engines answered `Success`: `SELECT EXISTS(SELECT 1) AS `db2.x`, count() FROM db1.o WHERE a IN `db2.x` SETTINGS enable_analyzer = 0` (the old analyzer's EXISTS rewrite drops the alias, so the operand reads the table; also from HAVING, ORDER BY, GROUP BY, LIMIT BY, PREWHERE, JOIN ON, INSERT … SELECT and CTAS) and `WITH tuple(1, 2) AS `db2.x` … WHERE a IN (SELECT … WHERE a IN `db2.x`) SETTINGS enable_analyzer = 0, legacy_column_name_of_tuple_literal = 1`. Rather than narrow the binding rules per analyzer, R5 refuses, with `table setting <name> is not accepted` (the name as written), in every settings position (query and subquery `SETTINGS`, INSERT header, view / MV body, command tail, CREATE storage `SETTINGS`, session `SET`) and both SI states: `enable_analyzer` and its alias `allow_experimental_analyzer` unless the value is a single literal whose raw lexeme is `1`, `true`, `'1'` or `'true'` (words in any case; measured true on both versions; every other spelling, including ones ClickHouse also reads as true such as `0x1`, `+1`, `1.0`, `x'31'`, `$$true$$`, and any expression or parameter, is refused); `legacy_column_name_of_tuple_literal` whatever the value; and `profile` whatever the value, because `SET profile = '<name>'` applies a server settings profile as a group (measured on both versions) and so could carry `enable_analyzer = 0`, like `compatibility`. `enable_scopes_for_with_statement` and the `analyzer_compatibility_*` settings stay accepted (no read under the new analyzer). The engines cannot see the native-protocol Query packet or a user's default profile: HouseGate's Query-packet check (Plan C) must refuse the same names with the same value rule, and deployments must keep the analyzer on in every profile. Shared corpus cases: `si_tr_setting_{analyzer_off_exists_alias,analyzer_off_tuple_legacy,experimental_analyzer_off,analyzer_string_false,legacy_tuple_name,profile}{,_v2}_rejected`, `si_tr_set_analyzer_off{,_v2}_rejected` and `si_tr_setting_analyzer_on{,_v2}_allowed`.
