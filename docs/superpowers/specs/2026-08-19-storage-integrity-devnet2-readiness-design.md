# devnet2 Pilot Readiness

**Date:** 2026-08-19 **Status:** Proposed **Roadmap:** [remediation roadmap](2026-08-19-storage-integrity-remediation-roadmap.md) Spec M. **Remediates:** [Spec F devnet2 deployment](2026-08-18-storage-integrity-devnet-deployment-design.md) as implemented on production branch `dev/uranus/storage-integrity-devnet2` (`3509fbae1`) — findings from the 2026-08-19 review. **Depends on:** Specs I, J, K, L merged and tagged. **Code base:** production `3509fbae1`, arbiter `71657a8`, arbiter-core `b669ccd`, network-da `8b67059`, sentio-node `ba136ea`, housegate `621eaab`. **Source of truth:** English version.

## 1. Problem

The deployment branch is well-built: the change is provably additive (rendered Helm output for `indexer-b`, un-overlaid `indexer-a` and `testnet-v2 observer` is byte-identical before and after), the schema constants are correct (recomputed independently with housegate's own `TableSchemaHash`/`SchemaRoot` from the committed `schema_json`), no secret material is committed, every state directory in the crash-recovery path lands on a PVC rather than an emptyDir, all four SI ClickHouse instances share one disk so hardlink promotion holds, the CHI zookeeper block matches the production keeper byte-for-byte, the four RMT replica names are distinct, and moving DA to a versioned delete-denied GCS bucket is an improvement over the spec's `fs`-on-PVC.

It nonetheless cannot pass its own §5 acceptance run.

**1a — nothing creates the ordinary physical table on the new ClickHouse.** The overlay repoints `indexer-a` from `clickhouse-devnet2-node-a` to a brand-new, empty `storage-integrity-source`. The SI lane still round-trips the INSERT through the ordinary physical table so ClickHouse can answer the Native sample block (only the rows are suppressed), and the rewriter targets the ordinary multi-tenant name, i.e. `devnet2.devnet101_swap_new2`. `--ensure-tables=create` builds only `hg_unsafe`/`hg_safe`/`hg_promote`. sentio-node's `database_registry` is an *observer*: it reacts to a user `CREATE TABLE` and registers it on chain; there is no path that reconciles the on-chain registry back into a fresh ClickHouse. The runbook's acceptance INSERT returns `UNKNOWN_TABLE`. The second-order effect is larger and undocumented: switching `indexer-a` to an empty ClickHouse strands *every* database and table it currently serves, and rollback restores the old ClickHouse while orphaning whatever was written to the new one.

**1b — the acceptance INSERT is rejected as a compressed payload.** The runbook uses a bare `clickhouse-client`; the C++ client enables native compression by default, and both the agent-side signer and the server-side ingress hard-reject compressed INSERT payloads. Every acceptance attempt fails with a message that reads like a product bug.

**1c — the anchor bootstrap Job is non-idempotent and its output is not durable.** `backoffLimit: 2` with `bind.DeployContract` (plain CREATE, no CREATE2) means a retry deploys a second registry with an empty `anchors` mapping; the command returns immediately after sending the transaction with no `WaitMined` anywhere in the repo, so it exits 0 on mempool acceptance; with up to three pods the runbook's `kubectl logs job/... | tail -n 1` cannot tell which attempt is real. The address then lives only in a hand-made Secret and the Job is deleted, while Spec F §2 requires it recorded in the production repo. The runbook's `eth_getCode` poll correctly compensates for the missing receipt wait and should be kept. Separately, the deploy and every subsequent `anchor()` are paid by `indexer-a`'s key with no balance monitoring, and the backpressure troubleshooting list does not mention poster balance — a dry poster stalls anchoring, freezes the safe watermark, stops promotion and drives `hg_unsafe` into the parts ceiling.

**1d — the arbiter and da-store images are likely unpullable.** The namespace supplies only a Google Artifact Registry pull secret, while both images are GHCR; neither repo's push workflow sets package visibility, and GHCR packages pushed from private repos default to private. The repo already has a `ghcr-image-secret` that this chart does not reference.

**1e — one private key is the client signer, the Arbiter authority and the EVM poster.** The chart points the authority secret at `sentio-node-devnet2-indexer-a-private-key` and feeds the same value into both authority and anchor environment variables; that key is also the agent's signing key and sentio-node's identity. Spec A's premise is that the operator side is untrusted once it merely forwards signed input, and Spec F §5's headline acceptance is a fraud drill — with one key in every role the pilot demonstrates the mechanism but not the property, and the §5 authority-rotation drill cannot be run without also rotating the indexer identity and the poster.

**1f — there are no metrics on any new component.** `prometheus|/metrics|metrics_listen|promhttp` returns zero hits across arbiter and arbiter-core; the arbiter opens exactly two listeners; all three config loaders use non-strict `yaml.Unmarshal`, so adding a `metrics_listen` key would be silently ignored. network-da starts no HTTP server. Spec F §6.2 made "minimal Prometheus metrics + `/metrics` in `cmd/arbiter`, `cmd/arbiter-verifier`, `cmd/arbiter-snode` (reuse housegate `pkg/metricshttp`)" an explicit deliverable of that spec; without it §4.9's dashboards cannot exist and the runbook's troubleshooting steps reduce to `kubectl logs`.

**1g — the runbook asserts an unimplemented behaviour.** It instructs the operator to restart a verifier and confirm it catches up; `Behind`/`CaughtUp`/`Lagging` are Spec D concepts and `safe_replica` has zero hits in all three Go repos. The chart correctly does *not* set `safe_replica`, so there is no config-ahead-of-code hazard — but the step is unvalidated and may pass or hang for reasons the operator cannot diagnose. Relatedly, Spec F §2 wanted Spec H's AnchorRegistry v2 so devnet2 would not carry a v1 anchor history; H has not landed, so v1 is the only option and the consequence is recorded nowhere.

**1h — the NetworkPolicy Spec F §2 assumes does not ship, and the data plane is open.** All four SI ClickHouse instances run `default` with an empty password, `networks/ip: 0.0.0.0/0` and `access_management: 1`; anything that can route to them can write `hg_safe` directly. network-da's TLS is a documented stub with no auth on either plane, so anything reaching the control port can call `ReleasePins`. The namespace is shared with blockscout, op-node, DinD and both indexers.

Medium items also worth folding in: two helmfiles own the same release, so a routine `helmfile apply` on the ordinary one silently reverts the pilot; the DA buckets are in `us-west1` while the cluster is `sentio-sea`, putting a trans-Pacific round trip on the ACK2 path; verifier pods have no probe and their Service points at a port nothing listens on, so `kubectl wait` goes green on a verifier that failed to register; `driver:dev` remains a moving tag for the workload that generates the pilot's writes; the four SI ClickHouse instances have no anti-affinity and can land on one node on `local-path` storage; `schemaRoot` is duplicated by hand across two values files with no cross-check, and the two sides resolve their schema from different sources (verifiers from an inline `tables:` block, the SNode from network state).

## 2. Goals / non-goals

Goals: (1) the §5 acceptance run completes end to end from a clean namespace using only committed manifests plus the documented secrets; (2) the fraud drill proves the property, not just the mechanism; (3) the operator can diagnose the pilot from metrics rather than logs alone; (4) the runbook describes what actually exists; (5) the pilot cannot be silently reverted or silently half-broken.

Non-goals: implementing Spec D or H (their absence is recorded, not fixed); TLS/mTLS on the DA planes (documented omission, unchanged); moving off `local-path`; multi-region DA.

## 3. Decisions

**D1 — Bootstrapping the ordinary physical surface is an explicit, chart-owned step.** Add a pre-install Job that creates the `devnet2` database and the pilot table on `storage-integrity-source` with the shape the on-chain registry declares, and make the runbook state plainly that `indexer-a` starts from an empty data plane — including which existing databases become unavailable and what the rollback does with data written in between. Rejected: teaching `database_registry` to reconcile chain state into ClickHouse — that is a real feature with its own correctness questions (ownership, drift, deletion) and does not belong in a pilot fix.

**D2 — Three distinct keys.** Generate a dedicated Arbiter authority key and a dedicated EVM poster key; the agent/indexer key stays as the client signer. `authority.allowed_addresses` carries the derived authority address, `ingress.allowed_addresses` carries the client address. This is a Secret plus two values, no code change, and it is what makes the §5 fraud drill and the rotation drill meaningful.

**D3 — The anchor deployment becomes recoverable, not merely un-retried.** `backoffLimit: 0` stops a second pod from deploying a second registry, but it does nothing for the case that actually loses state: the transaction mines and the pod dies before persisting the address. Recoverability comes from making the address knowable independently of the pod's output:
- **Pre-compute and persist the expected address before sending.** `CREATE` addresses are `keccak(sender, nonce)`, so `cmd/arbiter-anchor deploy` resolves the poster's pending nonce, derives the expected address, writes it to stdout **and** to a mounted path, and only then sends. A dead pod is then recovered by reading that path, or by re-deriving from `(sender, nonce)`, and confirming with `eth_getCode`.
- **`WaitDeployed`** before reporting success, so exit 0 means mined, not accepted.
- **Re-run safety**: on start, if the derived address already has code and its `stateRoot`/poster wiring matches, the command is a no-op success rather than a second deployment.
- The address is committed to a tracked `storage-integrity.json` in the production repo before the Job is deleted; a precheck asserts the poster balance is above a configured floor, and the runbook's backpressure checklist gains poster balance as a first-class item.

Rejected: CREATE2 with a salt — cleaner in principle, but it changes the contract's deployment interface for one pilot; nonce derivation gives the same recoverability with no contract change.

**D4 — Image pull is verified, not assumed.** Confirm anonymous pullability of both GHCR digests; if private, add `ghcr-image-secret` to the chart's `imagePullSecrets` and to the namespace. Add the check to the rollout precheck list so it fails fast rather than as `ImagePullBackOff`.

**D5 — Ship the metrics Spec F §6.2 already owed, in all four components the acceptance run names.** Add `/metrics` to `cmd/arbiter`, `cmd/arbiter-verifier`, `cmd/arbiter-snode` **and to network-da's `da-store`** (which today starts no HTTP server at all — it needs one added, with the same `metrics_listen` shape; the minimum series are put/fetch/pin counts and errors by code) via housegate's `pkg/metricshttp`, with a `metrics_listen` config key, and make all three loaders **strict** (`yaml.UnmarshalStrict` or `KnownFields(true)`) so an unknown or misspelled key is an error rather than silence — that strictness is what makes the config surface trustworthy going forward. Minimum metric set: admissions by code, blocks sealed, quorum verdicts, promotions issued/acked, cleanup acked, anchor height and lag, verifier dispatch/attestation counts. Chart adds the port and scrape annotations.

**D6 — The runbook describes only what exists.** Rewrite the verifier-restart step to state what is actually observable (re-dispatch on `dispatch.retry_interval`, not catch-up classes); add an explicit section recording that Specs D and H are not implemented, that the associated §5 criteria are deferred, that devnet2 will carry a v1 anchor history and will need a contract swap plus history reset when H lands, and that `AnchorRef.da_ref` stays empty so no L3 follower can be pointed at devnet2. Add `--compression=0` to every `clickhouse-client` invocation. Add "adding a safe replica" as an explicit N/A with the reason. Add the `dsnParams: ""` change as a rollback trigger, with the symptom (driver crash-loop / connection RST on BigInt entity columns) and a pre-rollout verification step against housegate v0.9.3.

**D7 — Isolation is enforced or explicitly disclaimed.** Ship the NetworkPolicy Spec F §2 assumed — restricting the SI ClickHouse and DA ports to the pilot's own pods — or, if that is deferred, state in the runbook that the isolation control is absent and what that means given the shared namespace. Do not leave the spec asserting an isolation mechanism that does not exist.

**D8 — Single-source the frozen identity and prevent silent reversion.** Derive `schemaRoot` in one place and reference it from both values files (or add a preflight `fail` that compares them); add a guard comment plus a distinguishing label so a `helmfile apply` on the ordinary file cannot silently revert the pilot release; give the verifiers a real readiness check or delete the phantom Service port; add anti-affinity across the four SI ClickHouse instances and the `spot: "false"` selector the other CHIs use; move the DA buckets to the cluster region; pin `driver:dev` or record it as a deliberate deviation.

## 4. Acceptance

The §5 run from a clean namespace: CHI ready with `system.zookeeper` reachable from all four instances → da-store answers `GetStoreLimits` → AnchorRegistry deployed, receipt confirmed, address committed → arbiter leader elected → schema declared on chain → all four nodes hold `hg_unsafe`/`hg_safe`/`hg_promote` with pinned settings → ordinary physical table exists → `indexer-a` rolled → INSERT of 1000 rows with `--compression=0` reaches ACK2 → `unsafe_latest` count 1000 immediately → after finality the safe watermark advances and `safe` count is 1000 → `hg_unsafe` parts return to 0 after cleanup → the fraud drill (payload swapped after signing, now with a distinct client key) returns `INVALID_SIGNATURE` → `indexer-b` still passes its existing checks → metrics are scrapeable for arbiter, verifiers and da-store.

## 5. Delivery

1. arbiter: nonce-derived address pre-computation, re-run no-op check and `WaitDeployed` in `cmd/arbiter-anchor`; `/metrics` + strict config in the three binaries → tag.
1b. network-da: a metrics listener and `metrics_listen` config key → tag.
2. production: D1 bootstrap Job, D2 keys, D3 Job and committed address, D4 pull secret, D6 runbook, D7 NetworkPolicy, D8 hygiene.
3. Rollout, then the §4 acceptance run recorded in the runbook with actual observed values.
